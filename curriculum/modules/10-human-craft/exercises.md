# Exercises

## Exercise 1: Turn a vague ask into a one-page spec
**id:** ex-1

Start with a vague request from your own work — something like "Make this better," "Help with the deck," or "Fix the email." Rewrite it as a one-page spec with five parts: outcome, audience, limits, sources, and three done checks. Each done check must be observable — someone else can say yes or no without guessing.

<details>
<summary>Answer key</summary>

A partner should execute without asking you three more questions. Done checks must be observable, not vibes like "sounds good."

**Worked example:** Vague: "Fix the email." Spec: Outcome: customer refund reply. Audience: upset buyer. Limits: no new offers or discounts. Sources: SOURCES.md policy row for refunds. Done: (1) cites policy line, (2) under 120 words, (3) plain tone with no legal jargon.

</details>

## Exercise 2: Practice reverse questioning
**id:** ex-2

Take a fuzzy ask from your work — one where you feel stuck on wording or scope. Write the instruction that forces **questions only — no draft yet**. Then list three answers you would give the helper before allowing any output.

<details>
<summary>Answer key</summary>

If the helper drafts anyway, stop it and reinforce the gate. Answer fully before allowing output. The three answers should remove the biggest ambiguities.

**Worked example:** Fuzzy: "Write about our product." Gate: "Ask five clarifying questions. Do not draft." Answers: audience = dentists; length = 300 words; tone = plain; source = BRIEF.md; no medical claims allowed.

</details>

## Exercise 3: Pick mode and approval rules
**id:** ex-3

For four tasks — email send, brainstorm, prod deploy, typo fix — choose **plan vs go** mode and whether **approval** is required. Write one reason per choice. High blast radius tasks need plan mode and approvals. Low-risk reversible work can use go mode with light gates.

<details>
<summary>Answer key</summary>

High blast radius → plan + approvals. Clear checklist work with low risk → go with light gates. Rubber-stamp approvals count as skipping the gate.

**Worked example:** Prod deploy → plan mode + approval required (high risk, hard to undo). Typo fix in draft doc → go mode, no approval (low risk, reversible). Email send → go mode + approval required (easy to undo draft, hard to undo send).

</details>
