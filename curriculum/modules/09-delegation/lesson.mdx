# Delegation and shared workspaces

## In plain words

- **Goal:** Split work safely and give the team one clear project room.
- **Do this:** Map the model, agent, harness, and optional framework. Share trusted files and rules. Give each job an owner, approval gate, and done checks.
- **You'll know it worked:** Teammates can explain what is shared, what stays personal, and who merges each result.

## What this is

**Delegation** means giving one clear job to a specialist. A **subagent** is like a specialist classmate with their own desk. You write a brief. They work. They return results. You merge.

An **agent harness** means the workbench around an agent. It supplies rules, tools, files, memory, approvals, logs, and checks.

An **agentic framework** means a builder kit for custom agent workflows. Builders use one when a ready-made harness cannot run the job safely.

A **shared workspace** is the team project room. It holds trusted sources, shared rules, recipe-card playbooks, tool setup, handoffs, and ownership.

## Why it matters

Priya gave two agents the same launch folder. One used an old price from memory. Both edited the same draft. Nobody knew which rules were current.

The model was not the main problem. The workspace had no source owner, edit boundary, or merge owner.

A clear harness and workspace would have stopped the collision. Delegation is not "more AI." It is smaller jobs inside safer boundaries.

## Big ideas

### Know the four layers

Do not treat every AI product as one mystery box.

1. The **model** reads words and writes words.
2. The **agent** can use tools and continue after results.
3. The **agent harness** supplies the workbench around that agent.
4. An **agentic framework** lets builders create a custom workflow.

Most teams can start with a ready-made harness. Add a framework only when you need custom steps, state, or approval paths.

### Check the harness

Use six checks before your team adopts a harness:

- **Tool fit** — Does it open only the apps this job needs?
- **State and memory** — Can the team inspect and correct saved facts?
- **Approval gates** — Does a person approve send, delete, pay, or deploy?
- **Visibility** — Can reviewers see tool calls, logs, and changes?
- **Portability** — Can you export the brief, sources, and handoff?
- **Collaboration** — Can people share rules without sharing private scratch work?

If a tool hides risky actions or saved facts, do not use it for that job.

### Write a shared workspace contract

Share only what the team needs:

- One canonical source for each important fact
- Short wall rules and named playbooks
- A small tool allow list and clear approval gates
- One handoff format for people and agents
- One owner for each editable output
- One merge owner for combined results

Keep experiments, rejected drafts, and personal chats outside the shared space.

**Design rule:** Shared truth needs one home. Shared edits need one owner.

### Keep the job contract

Every specialist brief still needs:

- Goal and inputs
- Allowed tools and approvals
- Out of scope
- Done checks
- Return format
- Output owner and merge owner

Run jobs together only when they own separate files, sections, rows, branches, or worktrees. Otherwise, run them one at a time.

### A simple walkthrough

You need a product launch one-pager.

1. **Map layers** — Your chat product is the harness. No framework is needed.
2. **Set shared truth** — BRIEF.md owns product facts. SOURCES.md owns proof.
3. **Split jobs** — A researcher returns cited bullets. A writer owns the draft.
4. **Set gates** — A person approves facts before the writer starts.
5. **Handoff** — The researcher returns ten bullets, not raw logs.
6. **Merge and verify** — One owner checks sources, scope, and done criteria.

If research fails verify, do not pass it to the writer.

## Where this sits in the loop

Delegation sits after memory and before human craft.

Memory brings trusted notes back. Delegation opens specialist desks. The harness controls which rules, tools, and checks surround those desks.

Results return through a handoff. One merge owner puts them back into the shared workspace.

## What goes wrong if you skip it

- The team buys a framework when a ready-made harness was enough.
- Personal memory becomes team truth.
- Conflicting rules steer different agents.
- Two helpers edit the same output.
- Risky actions run without approval.
- Logs vanish, so nobody can verify what happened.
- No merge owner combines and checks results.

## Tips

1. **Start with the harness you have.** Add a framework only for a real gap.
2. **Keep one home per fact.** Link to it instead of copying it.
3. **Separate scratch from shared truth.** Experiments should not steer teammates.
4. **Cap parallel helpers.** Start with two, not six.
5. **Verify sub-results before handoff.** Bad facts spread fast.
6. **Name the merge owner.** Shared work without one is unfinished.

The harness supplies the workbench. Your team still owns the work.
