# Memory systems

## In plain words

- **Goal:** Save facts for next time without storing junk, secrets, or stale guesses.
- **Do this:** Sort each fact into desk-only, binder note, or product sticky memory. Date facts that may change. Prune monthly.
- **You'll know it worked:** You open a fresh chat. The helper pulls facts from BRIEF.md, not from a wrong sticky note you forgot you set.

## What this is

Keep sticky notes for next time — that's **memory**. Some sit on today's desk only. Some live in a **binder** you control. Some live in the product's saved memory.

This lesson teaches three memory tiers. It shows what to save, what to prune, and what never to store.

You already use compaction from Module 7 to clear a busy desk. Memory is how facts come back on a later day — without re-teaching every time.

## Why it matters

Leo opened a new chat every Monday. Each time he re-explained the team name, the tone rules, and the project goal. That wasted twenty minutes a week.

Then Leo turned on product memory. The helper "remembered" a wrong launch date from a guess in October. That wrong sticky note haunted every draft for months.

Good memory saves time. Bad memory saves mistakes. **Binder notes you own** — like BRIEF.md — let you audit and fix facts.

## Big ideas

### Three places for facts

Think of three tiers:

1. **On the desk now** — this chat only. Great for today's draft and open questions.
2. **Binder notes you own** — BRIEF.md, wiki pages, tickets. You edit them. The team can read them.
3. **Product sticky memory** — saved preferences across chats. Harder to audit. Easy to forget you set it.

For important facts, prefer binder notes you can open and fix. Use product memory for light preferences — not secrets, not big tables.

**Design rule:** If a fact would hurt when wrong, put it in a binder note with a date — not in silent sticky memory.

The shared workspace should point to that binder note as the canonical source. Personal or product memory must not silently replace team truth.

### What to save

**Good to save:**

- Tone preference ("plain language, no hype")
- Stable team facts (name, product, support email)
- Project anchors (goal, owners, key links)

**Bad to save:**

- Secrets (API keys, passwords, private tokens)
- One-day guesses that were never verified
- Huge tables (put those in SOURCES.md and link instead)

Memory is not a junk drawer. Each sticky note should earn its place.

### What to prune

Memories go stale. Products change. Teams reorganize.

- **Delete** stickies that conflict or repeat binder notes.
- **Date** facts that may change ("Pricing as of March 2026").
- **Promote** stable process into wall rules (Module 3) or playbooks (Module 4).
- **Never store secrets** in chat memory or product memory. Rotate keys if you slipped.

Prune often — like clearing old sticky notes off your monitor.

### A simple walkthrough

Your team starts a support-bot project.

1. **Desk** — Today's chat tests three sample replies. Do not save drafts to memory.
2. **Binder** — Update BRIEF.md with goal, users, and support limits. Link SOURCES.md.
3. **Product memory** — Save only "Reply in friendly plain language."
4. **Weekly prune** — Open memory settings. Delete the old "beta pricing" sticky. Add dated pricing to SOURCES.md instead.
5. **Verify** — Open a fresh chat. Does the helper pull facts from BRIEF.md? If not, fix retrieval (Module 6), not more stickies.

If step 5 fails, you may have duplicated facts in three places. Pick one canonical home.

## Where this sits in the loop

Memory is sticky notes and binder notes that re-enter the desk later. It sits after compaction and before delegation.

- Module 7: compaction (short note to clear desk)
- Module 8: memory (sticky notes for later — this lesson)
- Module 9: delegation (specialist desks)

Durable notes load beside wall rules. They may load quietly. That is why you prune and date them.

## What goes wrong if you skip it

- You re-teach the same facts every chat. Time drains away.
- Wrong stickies return forever. Nobody remembers who set them.
- Secrets land in product memory. That is a security risk.
- Binder and memory disagree. The helper picks the wrong one.
- Huge tables in memory overflow the desk when they load.
- Teams skip pruning. Old folklore becomes "what the AI knows."

## Tips

1. **Write facts with dates** so stale stickies are obvious.
2. **Never store secrets in memory** — use a vault, not a chat.
3. **Link to a canonical doc** instead of restating a long policy.
4. **Audit monthly** — open product memory and delete three stale items.
5. **One home per fact** — BRIEF.md or memory, not both with different wording.
6. **Promote stable habits** into wall rules when a sticky repeats every week.

Memory should feel like a labeled binder — not a messy backpack.
